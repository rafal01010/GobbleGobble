# Backend API

The API currently bootstraps anonymous sessions, admits queued runs, reads their state and streams committed events. It does not yet resolve locations through HTTP, execute production research, publish recommendation versions or expose refinement/retry/cancel routes. A [controlled worker](SETUP.md#run-a-diagnostic-job) advances an explicitly selected run without food research.

[application.py](../apps/backend/app/api/application.py) owns routes and the HTTP boundary. The Pydantic [domain models](DOMAIN.md) are authoritative payload definitions. The complete HTTP/database/worker flow still needs integrated runtime verification; the examples below are contracts, not observed restaurant searches.

## Implemented HTTP operations

Start the API using [local setup](SETUP.md#start-the-api). App construction and contract export require no storage access; request handlers open existing storage and do not migrate it.

| Method and path | Success | Behavior |
|---|---|---|
| `GET /ready` | 200 `{"status":"ready"}` | Checks complete migration history and checksums. Does not repair storage or claim worker/provider readiness. |
| `POST /api/session` | 204, empty | Issues a session only for an absent cookie. Resolves an existing cookie without rotation; invalid/empty credentials receive 401. |
| `POST /api/runs` | 202 `CommandResponse` | Commits queued admission or replays the current durable snapshot without waiting for research. |
| `GET /api/searches/{search_id}/runs/{run_id}` | 200 `RunReadResponse` | Authorizes the search and selects the run by both IDs. Recommendations are not stored yet. |
| `GET /api/searches/{search_id}/runs/{run_id}/events` | 200 `text/event-stream`, or 204 when terminal and caught up | Replays after a sequence, then follows newly committed events. |

## Sessions and errors

Complete bootstrap before concurrent authenticated requests. Subsequent requests send the host-only `gg_session` cookie with `HttpOnly`, `Path=/` and `SameSite=Lax`. HTTPS or `GG_SESSION_COOKIE_SECURE=true` sets Secure. There is no Domain, persistent expiry, rotation or recovery mechanism. Trust the configured request scheme, not arbitrary forwarded headers.

Every POST, PUT, PATCH or DELETE needs exactly one `Origin` matching a configured frontend origin before body parsing/storage. Missing, duplicate, `null` and unmatched origins receive 403. Credentialed CORS permits configured origins, GET/POST, Content-Type and Last-Event-ID. Rejected preflights use the fixed 400 envelope. All responses use `Cache-Control: no-store`. See [settings](SETTINGS.md) for exact origin configuration.

Resource IDs alone grant no access. Foreign, unknown and mismatched search/run pairs share the same 404, including when the browser owns both searches. Browser credentials are separate from request payloads, worker lease credentials and URL parameters.

`ErrorResponse` wraps `OperationError` with these fixed values:

| HTTP status | Code and message | Retryable |
|---|---|---|
| 400 | `invalid_request`, `cors_not_allowed` | false |
| 401 | `invalid_request`, `invalid_session` | false |
| 403 | `invalid_request`, `origin_not_allowed` | false |
| 404 | `not_found`, `not_found` | false |
| 405 | `invalid_request`, `method_not_allowed` | false |
| 409 | `command_conflict`, `command_conflict` | false |
| 422 | `invalid_request`, `invalid_request` | false |
| 500 | `unavailable`, `internal_error` | false |
| 503 | `unavailable`, `storage_unavailable` | true |

Rejected-operation errors are distinct from an admitted run completing with `technical_failure`. The boundary returns no framework validation detail, submitted input, raw exception or traceback. It logs a fixed synthetic `api_request_failed` diagnostic rather than the original exception. After response headers start, it raises only sanitized `api_response_interrupted` and terminates transport; it cannot replace the body with an error envelope. External server/proxy logging requires separate configuration.

## Expected request and response examples

The cookie marker and resource IDs are illustrative. The actual credential is generated by the server and delivered through Set-Cookie.

```http
POST /api/session HTTP/1.1
Host: localhost:8000
Origin: http://localhost:5173
```

```http
HTTP/1.1 204 No Content
Set-Cookie: gg_session=<server-generated-credential>; HttpOnly; Path=/; SameSite=lax
Cache-Control: no-store
```

The start operation currently accepts an already resolved request. It does not perform location lookup. Supply a current aware dining instant when exercising it; this date is illustrative.

```http
POST /api/runs HTTP/1.1
Host: localhost:8000
Origin: http://localhost:5173
Cookie: gg_session=<server-generated-credential>
Content-Type: application/json

{"command_id":"controlled-start-1","request":{"origin":{"kind":"current","location":{"coordinates":{"latitude":14.6,"longitude":121.0},"timezone":"Asia/Manila","provider_refs":[]}},"travel":{"mode":"walk","minutes":15},"eat_now_at":"2026-10-26T12:00:00+08:00"}}
```

First admission returns HTTP 202 with this body after the transaction commits:

```json
{"command":{"disposition":"accepted","command_id":"controlled-start-1","run":{"search_id":"example-search","run_id":"example-run","operation":"initial","attempt_id":null,"state":{"status":"queued"},"last_event_sequence":1}}}
```

Identical normalized input replays the same identities with `disposition: "replayed"` and current persisted state, which may have advanced. Conflicting command reuse returns 409:

```json
{"error":{"code":"command_conflict","message":"command_conflict","retryable":false}}
```

Read without admitting another run:

```http
GET /api/searches/example-search/runs/example-run HTTP/1.1
Host: localhost:8000
Cookie: gg_session=<server-generated-credential>
```

The HTTP 200 body is:

```json
{"run":{"search_id":"example-search","run_id":"example-run","operation":"initial","attempt_id":null,"state":{"status":"queued"},"last_event_sequence":1},"recommendations":null,"display_version_id":null}
```

## Event stream

The events endpoint requires the same cookie and paired authorization. Optional query `after_sequence` defaults to zero. A supplied `Last-Event-ID` overrides the original query cursor, allowing automatic reconnect to advance. Both supplied values must be valid even when the header wins.

Each cursor accepts one ASCII decimal string of one through nineteen digits between zero and 9223372036854775807. Empty, duplicate, signed, whitespace, fractional, non-ASCII and oversized values receive 422. A cursor ahead of the authorized run's durable sequence also receives 422 before SSE headers.

A stream uses `text/event-stream`, no-store and `X-Accel-Buffering: no`. Each frame has a run-scoped sequence as `id` and the stored `RunEvent` JSON as `data`, followed by a blank line. There is no named event field, so EventSource clients use `onmessage` and `withCredentials: true` on the configured frontend origin.

```text
id: 1
data: {"schema_version":1,"search_id":"example-search","run_id":"example-run","attempt_id":null,"sequence":1,"occurred_at":"2026-10-26T00:00:00Z","result_version_id":null,"payload":{"kind":"queued"}}

```

Opening and idle comments carry no ID and never advance the cursor. Reconnect after the last accepted event and deduplicate by run plus sequence. The protocol follows the [HTML SSE specification](https://html.spec.whatwg.org/multipage/server-sent-events.html).

The API authorizes and reads the first batch before sending headers. Replay and follow use the same suffix query after the delivered cursor, with no process-local registration window. Each poll opens and closes its own thread-owned connection and short deferred read transaction. Authorization, paired run lookup and event read share one snapshot. No connection survives a send or wait.

Batches hold at most 100 events. Backlog drains without an idle wait; caught-up streams poll every 250 milliseconds with ID-free idle comments every 15 seconds. These are defaults, not measured delivery guarantees. Sends apply backpressure. One disconnect listener races the sender; disconnect ends only the subscription, never the durable run. An active threadpool read finishes cleanup before cancellation starts no further poll.

The controlled worker supports completed coverage-gap and technical-failure histories. Streams drain their terminal events and close; a reconnect already at that cursor returns 204. Clients should close EventSource after accepting terminal completion. Other terminal writers are incomplete. After-header failures interrupt transport without inventing events or inserting error JSON. No watcher retention/expiry policy or measured subscriber capacity exists; current history validation scans the run index.

## Export the contract

After [backend installation](SETUP.md#initialize-backend-storage), run from the repository root:

```sh
mkdir -p data/verification/api-contract
cd apps/backend
.venv/bin/python -m app.schema_export > ../../data/verification/api-contract/openapi.json
```

The module writes deterministic OpenAPI 3.1.0 JSON to stdout and exits zero on success. Generation/output failure exits nonzero; redirection may leave a partial file, so do not consume it after failure. `--help` exits zero; other arguments fail with exit 2 and no JSON. No environment, credential, database, server or network access is needed.

[schema_export.py](../apps/backend/app/schema_export.py) combines real route metadata with retained model definitions, requires shared components to agree and rejects unresolved references. Input/output schema modes can differ. Generated JSON is not a second source to edit.

## Operation payloads

[operations.py](../apps/backend/app/schemas/operations.py) also defines location resolution, finite food-choice/all-options, retry and cancellation payloads. Their presence in the export does not mean routes exist. [Domain validation](DOMAIN.md) describes outcome/result identities, branch support, choice lineage and strict nullable fields.

Frontend API type generation is not implemented yet. It must consume this canonical export, including event types, instead of maintaining handwritten parallel wire interfaces. JSON Schema and TypeScript cannot replace the backend's relationship validators.

Actual cookie/CORS behavior, cross-owner isolation, stream delivery/disconnect, rollback, concurrency and restart still need integrated verification. No complete application or live recommendation success follows from export, model parsing or the illustrative payloads above.
